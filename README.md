# Lie-of-Omission Detector (Verity)

Verity is a full-stack AI-powered application designed to detect "lies of omission" in insurance claims. It uses Vision Language Models (VLMs) and Large Language Models (LLMs) to automatically analyze claimant-submitted evidence (images and documents) and cross-reference them against the stated claims to flag unsupported, contradicted, or missing evidence.

## Workflow Architecture

The application is built using a modern, scalable architecture:

1. **Frontend (React + Vite + TailwindCSS)**: Provides an intuitive wizard for claimants to upload evidence, review AI-extracted information, and generate a final PDF claim form. It also includes an admin dashboard for adjusters to review flagged claims. Authentication is handled via **Clerk**.
2. **Backend (FastAPI + Python)**: The core engine that orchestrates the AI pipeline, handles file uploads, and manages database interactions. PDF generation and text extraction (using `pdfplumber` and `reportlab`) are also handled here.
3. **Database (MongoDB)**: Stores case data, user information, and AI analysis results.
4. **AI Pipeline (Groq + Ollama)**:
   - **Primary Provider (Groq)**: Uses high-speed LLMs (e.g., Llama 3) for text extraction and Vision models for image analysis.
   - **Fallback Provider (Ollama)**: A local, open-source fallback to ensure the pipeline doesn't break if cloud APIs are rate-limited.

## API Workflow Structure & Process

The Verity backend exposes a REST API built with FastAPI that orchestrates the AI reasoning pipeline. The system operates in two distinct flows depending on whether the user is generating a new claim from evidence or applying directly using a manually filled form.

### 1. Claim Generation Workflow (AI-Assisted)
This workflow is used when a claimant uploads raw evidence (photos, police reports, repair estimates) and wants the AI to draft the claim for them.

*   **Step 1: Evidence Upload & Initial Description (`POST /claim-generator/describe`)**
    *   **Action**: The frontend sends the uploaded images and documents to the backend.
    *   **Process**: The backend saves the files locally. It calls the **Vision Model** to describe any damage in the images and checks if they are relevant to the claim category. It uses `pdfplumber` and the **Text Model** to extract any plain text fields from PDFs/Word docs.
    *   **Response**: Returns AI-generated descriptions of the damage, text fields extracted from documents, and a list of follow-up questions generated by the AI to clarify ambiguities.
*   **Step 2: Drafting the Claim (`POST /claim-generator/{case_id}/draft`)**
    *   **Action**: The user answers the AI's follow-up questions, and the frontend submits these answers.
    *   **Process**: The backend feeds the original evidence descriptions + the user's Q&A answers into the **Text Model**. The LLM synthesizes this context to draft a structured set of claims.
    *   **Response**: Returns the drafted claims, suggestions for further evidence, and a preview of the generated claim form.
*   **Step 3: Review & PDF Generation (`GET /claim-generator/{case_id}/pdf`)**
    *   **Action**: The user reviews the drafted claims, makes manual edits, and clicks "Download PDF".
    *   **Process**: The backend takes the finalized template data and uses `reportlab` to generate a formatted, industry-standard PDF claim document.

### 2. Direct Apply Workflow (Manual Entry)
This workflow is used when a claimant manually fills out a claim form and uploads evidence, triggering the AI to vet the submitted evidence against their stated claims.

*   **Step 1: Submit Application (`POST /applications`)**
    *   **Action**: The claimant submits their completed form data alongside their supporting evidence (photos).
    *   **Process**: The backend creates a new "Case" in MongoDB with a `pending_processing` status. It saves the raw form data and the file paths for the uploaded evidence.
    *   **Response**: Returns the newly created `case_id`.
*   **Step 2: Background AI Pipeline Execution (`Background Tasks`)**
    *   Once the application is submitted, a background worker triggers the core AI reasoning pipeline:
    *   **Extraction**: The LLM parses the user's form data into standardized JSON claims.
    *   **Vision Analysis**: The Vision Model analyzes the submitted photos independently, documenting exactly what is visible (and what is unexpectedly *not* visible).
    *   **Contradiction Check**: The LLM cross-references the extracted claims against the vision analysis to flag any "lies of omission" (e.g., the user claims the front bumper is destroyed, but the photo only shows the rear bumper).
    *   **Policy Screening**: The claims are checked against company policy rules (e.g., "Theft claims require a police report").
*   **Step 3: Admin Review (`GET /cases/{case_id}`)**
    *   **Action**: An insurance adjuster logs into the Admin Dashboard to review the case.
    *   **Process**: The frontend fetches the results of the background AI pipeline, displaying a comprehensive report of any flagged contradictions, missing evidence, or policy violations for the adjuster to make a final decision.

## Setup Instructions

### Prerequisites
- [Docker & Docker Compose](https://www.docker.com/) (Recommended for easy setup)
- [Node.js](https://nodejs.org/) (v18+)
- [Python](https://www.python.org/) (3.11+)
- [MongoDB Atlas](https://www.mongodb.com/) Account (or local MongoDB)
- [Clerk](https://clerk.dev/) Account (for Authentication)
- [Groq](https://console.groq.com/) API Key

### 1. Environment Configuration
You need to set up three `.env` files across the project.

**Root `.env` (Used by Docker):**
Create a `.env` file in the root directory. You can copy the provided `.env.example` file and fill in your keys:
```bash
cp .env.example .env
```

```env
VITE_CLERK_PUBLISHABLE_KEY=your_clerk_publishable_key
GROQ_API_KEY=your_groq_api_key
PRIMARY_PROVIDER=groq
FALLBACK_PROVIDER=ollama
OLLAMA_BASE_URL=http://host.docker.internal:11434
MONGODB_URI=your_mongodb_connection_string
CLERK_SECRET_KEY=your_clerk_secret_key
```

**Backend `.env` (For local development):**
Located in `/backend/.env`. Copy the contents of the root `.env` here, but change `OLLAMA_BASE_URL` if running locally without Docker:
```env
OLLAMA_BASE_URL=http://localhost:11434
```

**Frontend `.env` (For local development):**
Located in `/frontend/.env`:
```env
VITE_API_URL=http://localhost:8000
VITE_CLERK_PUBLISHABLE_KEY=your_clerk_publishable_key
```

### 2. Running the Application (Docker - Recommended)

The easiest way to run the full stack is using Docker Compose. From the root of the project, simply run:

```bash
docker-compose up --build
```
- The **Frontend** will be available at `http://localhost:8080`
- The **Backend API** will be available at `http://localhost:8000`
- The **Swagger UI** for the API will be at `http://localhost:8000/docs`

### 3. Running the Application Locally (Without Docker)

If you prefer to run the services directly on your machine for development:

**Start the Backend:**
```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --reload
```

**Start the Frontend:**
```bash
cd frontend
npm install
npm run dev
```

### 4. Obtaining API Keys

#### Clerk (Authentication)
1. Go to [Clerk.com](https://clerk.com/) and create a free account.
2. Create a new application.
3. On the dashboard, find your **API Keys**.
4. Copy the `Publishable key` to `VITE_CLERK_PUBLISHABLE_KEY` and the `Secret key` to `CLERK_SECRET_KEY`.

#### Groq (AI Models)
1. Go to the [Groq Cloud Console](https://console.groq.com/) and sign in.
2. Navigate to the **API Keys** section from the left sidebar.
3. Click "Create API Key".
4. Copy the key and paste it into `GROQ_API_KEY`. (Note: Groq offers a generous free tier, no credit card required).

#### MongoDB Atlas (Database)
1. Sign up for a free tier database at [MongoDB Atlas](https://www.mongodb.com/cloud/atlas).
2. Create a new cluster (the M0 free tier is perfectly fine).
3. Under "Database Access", create a new database user with a username and password.
4. Under "Network Access", allow access from anywhere (`0.0.0.0/0`) or your specific IP.
5. Go to your cluster, click **Connect**, select "Drivers", and copy the connection string.
6. Replace `<password>` with your database user's password and paste it into `MONGODB_URI`.

## Key Features
- **Smart Evidence Extraction**: Upload a PDF or Image, and the AI automatically extracts relevant fields (Date, Location, Witnesses, etc.) to pre-fill the claim form.
- **Visual Damage Assessment**: Analyzes images of damaged vehicles to cross-reference against the user's claims.
- **Automated PDF Generation**: Generates a professional, standardized PDF claim form pre-filled with the AI-extracted and user-verified data.
- **Omission Detection**: Flags discrepancies where the submitted photo does not show the damaged areas described in the claim.
